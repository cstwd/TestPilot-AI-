# TestPilot AI 大规模测试代码实验室建设任务

## 一、任务目标

请在现有 TestPilot AI 项目中，独立建设一个规模化、专业化、可持续扩展的 Python 测试代码库，作为 TestPilot AI 的官方演示数据集、功能验收数据集和 AI 测试能力评估数据集。

项目位置：

`D:\TestPilot AI`

代码库位置：

`D:\TestPilot AI\demo\TestPilot-Demo-Lab`

本任务不是编写几个简单的教学例程，而是建设一套具有真实软件工程特点的测试样本库。

核心目标：

1. 提供大量正确实现的 Python 源码。
2. 提供大量故意植入 Bug 的 Python 源码。
3. 提供具有复杂边界条件和隐蔽逻辑错误的挑战样本。
4. 让 TestPilot AI 自己分析源码、生成测试、执行测试和发现缺陷。
5. 建立独立的标准答案库，用于验证 AI 是否真正发现了问题。
6. 支持 F01、F02、F03、F04、F05、F06 和 F13 完整演示。
7. 能够批量扩展样本，形成长期测试基准。

直接执行建设，不要只提交计划或等待人工编写代码。

## 二、总体规模

第一版目标建设 100 个独立 Python 源码模块。

| 类型 | 数量 | 用途 |
|---|---:|---|
| 正常代码 GOOD | 25 | 验证正常代码的测试生成能力 |
| 缺陷代码 BUGGY | 50 | 验证 AI 缺陷发现能力 |
| 综合挑战 CHALLENGE | 25 | 验证复杂逻辑和边界测试能力 |
| 合计 | 100 | 完整测试代码库 |

数量是建设目标，不允许通过复制粘贴、简单改名或重复逻辑凑数。

每个模块应具有独立功能、清晰接口和真实测试价值。

建议建设：
- 至少 150 个独立可识别的缺陷实例。
- 至少 300 个独立验证测试用例。
- 至少 50 个边界条件测试场景。
- 至少 30 个异常处理测试场景。
- 至少 20 个多条件组合逻辑测试场景。

每个模块保持适合单文件导入的规模，优先控制在 128 KiB 以内。

## 四、代码编写规范

所有源码必须遵循以下要求：

1. Python 3.10+ 兼容，优先兼容项目实际 Python 3.13 环境。
2. 使用标准库优先，不依赖付费 API。
3. 每个文件可以独立导入。
4. 每个文件至少提供 2 个有实际意义的顶层同步函数，优先满足 F03 当前的函数选择能力。
5. 函数必须有清晰的名称、参数、返回值和 Docstring。
6. 输入输出尽可能确定，避免随机行为。
7. 不允许通过故意语法错误来制造 Bug。
8. 不允许用简单的固定异常代替真实逻辑缺陷。
9. 不允许在源码中暴露缺陷答案。
10. 不允许将正确实现和错误实现混在同一演示文件中。

BUGGY 文件必须保持 Python 语法有效、可以导入、能够执行。

每个缺陷必须能够通过特定输入触发，并产生可观察的错误结果。

## 五、标准答案与隐藏评测数据

建立独立参考答案库：

`reference/`

至少包含：

- 正确版本源码。
- 缺陷版本对应的正确实现。
- 缺陷编号。
- 缺陷类别。
- 正确输入。
- 正确输出。
- 实际错误输出。
- 预期异常。
- 触发缺陷的测试输入。
- 修复前后的行为差异。

建立：

`reference/ground_truth.json`

作为独立评测标准。

重要要求：

ground_truth.json 不得被导入 TestPilot AI 的源码分析、测试生成、执行和缺陷检测流程。

实际 AI 测试过程中，只允许导入 source/ 下的待测代码。

标准答案只能由独立评测程序读取，用于测试完成后的结果核对。

不得通过文件名、函数注释、Docstring 或接口参数直接向 AI 暴露缺陷答案。

## 六、独立测试体系

建立独立验证测试集。

目录：

`tests/`

每个源码模块必须有对应的独立验证测试。

测试内容包括：

1. 正常输入。
2. 最小输入。
3. 最大输入。
4. 空值。
5. 非法类型。
6. 边界值。
7. 特殊数值。
8. 异常处理。
9. 多条件组合。
10. 回归测试。

GOOD 模块的验证测试应全部通过。

BUGGY 模块的验证测试应能够稳定复现对应缺陷。

CHALLENGE 模块必须包含针对组合逻辑的测试。

要求：
- 使用 pytest。
- 每个测试具有明确断言。
- 不依赖网络。
- 不依赖真实数据库。
- 不依赖随机测试结果。
- 不允许为了通过测试而修改预期结果。
- 不允许跳过失败用例来制造全绿结果。

验证测试与 AI 实际生成的测试套件必须物理隔离。

## 七、Mutation Testing 专项设计

充分利用 TestPilot AI 的 F13 模块。

挑选至少 15 个适合变异测试的正确源码函数。

重点考察：

- 比较运算符变异。
- 算术运算符变异。
- 布尔逻辑变异。
- 返回值变异。
- 条件分支变异。
- 边界常量变异。

每个样本都必须先有有效的原版测试基线。

之后使用 F13 生成并执行变异，观察测试能否杀死变异。

记录：
- 变异总数。
- 已杀死数量。
- 存活数量。
- 错误数量。
- 超时数量。
- 等价候选数量。
- 最终 Mutation Score。

不得人为修改 Mutation Score。

## 十、独立评估指标

实现独立评测程序，至少计算：

1. Bug Detection Rate：已知缺陷检出率。
2. Test Pass Rate：正常代码测试通过率。
3. False Positive Rate：正常代码误报率。
4. Boundary Test Coverage：边界测试场景覆盖率。
5. Regression Pass Rate：修复后回归通过率。
6. Mutation Score：变异测试得分。

所有指标必须有明确分子、分母和统计口径。

注意区分：
- AI 生成了测试。
- 测试成功执行。
- 测试真正发现了缺陷。
- 缺陷经过正确修复。
- 回归测试验证修复有效。

不能把测试代码生成数量当成缺陷检出数量。

不能把代码行覆盖率当成逻辑正确率。
