本阶段由陈帅廷负责整体开发、架构决策、集成和验收。其他成员的参与和贡献必须以真实交付记录为依据。

## 3. 核心开发任务

### F07：Code Analyzer

使用 Python AST 建立源码分析模块。



要求：

- 识别函数、类、方法及其参数。
- 识别返回值、默认参数和异常。
- 提取类型注解和文档字符串。
- 识别条件分支、循环和关键逻辑。
- 分析可测试入口及依赖关系。
- 处理语法错误、编码错误和不支持的源码结构。

输出标准化 JSON 分析结果。

### F08：Test Strategy Engine

根据源码分析结果自动生成测试策略。



至少覆盖：

- 正常输入。
- 边界输入。
- 空值和缺失参数。
- 非法数据类型。
- 异常输入。
- 特殊数值。
- 条件分支。
- 返回值约束。
- 异常行为。

测试策略必须说明测试目的、输入、预期输出和测试类型。

### F09：AI Test Generation Engine

将现有模板引擎升级为真正的 AI 测试生成引擎。



要求：

- 实现统一 LLM Adapter。
- 支持不同模型供应商和本地模型接入。
- 支持模型配置、超时、重试和错误处理。
- 将源码上下文与测试策略传入模型。
- 生成可执行 Pytest 测试代码。
- 进行 Python AST 语法检查。
- 检查测试文件是否包含有效测试函数。
- 生成失败时记录原因并提供可解释的降级方案。

禁止将模板生成结果标记为 AI 生成结果。



如果没有可用模型，必须明确展示当前使用的是规则模式或模板模式。

### F10：Sandbox Execution Engine

实现安全测试执行系统。



要求：

- 测试代码独立进程执行。
- 源码和测试文件使用独立临时工作目录。
- 设置执行超时。
- 限制内存、进程数和输出大小。
- 尽可能限制网络访问和文件系统访问。
- 捕获 stdout、stderr 和退出码。
- 支持 Pytest JSON 结果解析。
- 支持 Coverage.py 行覆盖率和分支覆盖率。
- 保留执行记录。

不得在平台 Web 服务主进程中执行不可信测试代码。

### F11：Failure Analysis Engine

自动分析测试执行结果。



要求：

- 区分测试失败、测试错误、跳过和超时。
- 解析 Traceback。
- 定位失败测试函数。
- 提取断言差异。
- 识别异常类型。
- 给出可能的缺陷位置和原因。
- 输出结构化缺陷报告。

必须区分真实程序缺陷、测试代码错误和执行环境问题。

### F12：Feedback & Repair Engine

建立测试反馈与修正机制。



要求：

- 根据失败信息分析测试用例。
- 判断是否为生成的测试本身存在问题。
- 必要时重新生成测试。
- 重新执行并记录结果。
- 保留初次失败和修正后结果。
- 限制最大反馈循环次数。
- 防止重复生成相同测试。
- 禁止自动修改用户原始源码。

## 4. 统一数据结构

建立标准化数据模型：

- SourceAnalysis
- TestStrategy
- GeneratedTest
- TestExecution
- CoverageResult
- FailureAnalysis
- RepairAttempt
- TestReport

每个任务应具备唯一 ID、时间戳、执行状态和关联记录。

## 5. 端到端验收用例

至少建立以下真实测试项目：

1. 正确实现的快速排序。
2. 存在负数处理缺陷的函数。
3. 存在空输入问题的函数。
4. 存在边界条件错误的函数。
5. 存在异常处理错误的函数。
6. 存在多分支逻辑的函数。

验收必须证明：

- 引擎能够读取真实源码。
- 能够生成真实 Pytest 测试文件。
- 测试文件能够实际执行。
- 能够发现预置缺陷。
- 能够区分测试代码错误和程序缺陷。
- 能够采集覆盖率。
- 能够生成结构化报告。
- 能够保存完整执行历史。
