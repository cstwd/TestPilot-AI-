# WP06-F04-001

# TestPilot AI · Test Execution Control Center

## 一、任务目标

完成 F04 自动化测试执行页面的产品级视觉升级。



以 F01、F02、F03 已完成的 Design System V1 为统一设计基准。



视觉定位：



Professional Dark Testing Control Center



保留现有 Jinja + CSS + 原生 JavaScript 架构。

## 二、实施前审计

检查：

- 当前 Git HEAD 和工作区状态。
- runs.html。
- runs.js。
- backend/runs.py。
- backend/runner.py。
- 现有执行 API 和数据模型。
- F04 现有自动化测试。
- F01–F03 公共组件。

特别核查当前执行器的真实运行方式、响应时机、日志持久化和并发限制。



不得假设存在 SSE、WebSocket 或逐行日志流。

## 三、页面设计

### 1. 顶部执行上下文

展示：

- 当前项目。
- 被测文件。
- 被测文件版本。
- 测试套件。
- 套件来源版本。
- 当前运行 ID。
- 执行状态。

明确区分套件来源版本和实际被测版本。

### 2. 左侧运行历史

实现：

- 历史运行列表。
- 运行 ID。
- 执行时间。
- 真实终态。
- 测试统计摘要。
- 运行筛选。
- 历史记录切换。

切换运行后，所有详情必须同步切换，不得混用不同运行的数据。

### 3. 中央执行工作区

顶部执行控制：

- 选择套件。
- 选择被测版本。
- 执行测试按钮。
- 重复提交保护。

执行摘要：

- Passed。
- Failed。
- Error。
- Skipped。
- 实际执行耗时。

测试用例表：

- nodeid。
- 测试名称。
- 状态。
- 耗时（存在真实字段时）。
- 错误摘要。
- 关联缺陷入口。

优先展示失败和错误用例，同时保留完整列表。

### 4. 右侧 Inspector

提供：

- 测试用例名称。
- nodeid。
- 执行状态。
- 失败断言。
- 错误类型。
- 文件与行号。
- 原始错误堆栈。
- 进入缺陷管理入口。

只显示后端实际提供的信息。

### 5. 底部 Execution Console

展示：

- 真实执行日志。
- 原始输出顺序。
- 日志搜索。
- 日志复制。
- 输出截断提示。
- 空日志状态。

支持折叠与展开。

## 四、真实交互

1. 从 F03 接收真实套件 ID。
2. 核对套件来源版本。
3. 选择被测文件版本。
4. 提交执行请求。
5. 展示真实等待状态。
6. 防止重复提交。
7. 响应完成后展示运行 ID。
8. 展示该运行的真实用例和日志。
9. 点击失败用例查看详情。
10. 点击缺陷入口进入 F05。
11. 可以重新打开历史运行。
12. 刷新后能够恢复可追溯的运行上下文。

## 五、状态真实性要求

严格区分：

- 请求等待中。
- 执行完成。
- 执行失败。
- 测试断言失败。
- 执行器不可用。
- 执行超时。
- 并发冲突。
- 无日志输出。
- 日志截断。

HTTP 请求成功不等于所有测试通过。



测试断言失败不等于测试执行器发生故障。



当前没有真实日志流，不允许使用模拟终端输出。

## 六、视觉要求

- 继承 F01–F03 深色 Design System。
- 紫色用于主操作。
- 蓝色用于普通交互。
- 绿色、红色、橙色用于真实业务状态。
- 终端采用 JetBrains Mono 或本机回退字体。
- 保持面板层次、细边框和统一间距。
- 桌面端优先，移动端顺序阅读。
- 支持历史列表和详情面板折叠。

## 七、回归与安全要求

- 不修改执行器核心逻辑。
- 不修改 API 契约。
- 不修改数据库结构。
- 不突破现有受限执行边界。
- 不执行前端提交的任意宿主命令。
- 保留现有并发保护。
- 保留日志大小和输出截断限制。
- 不把错误状态误显示为成功。
- 不破坏 F01→F02→F03→F04 业务主线。

## 八、验收案例

至少覆盖：

1. 全部通过的运行。
2. 断言失败的运行。
3. 执行错误。
4. 执行器忙。
5. 执行超时。
6. 空日志。
7. 输出截断。
8. 历史运行切换。
9. 运行刷新恢复。
10. 从失败用例进入 F05。

所有结果必须使用真实后端记录或明确标识的故障注入。
